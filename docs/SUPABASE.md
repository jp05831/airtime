# PostgreSQL, authentication and private storage

1. Create a separate AIRTIME Supabase project. Do not use CUT’s database or keys.
2. Set `DATABASE_URL` to the Supabase **session pooler** connection copied from the Dashboard, using port `5432` (not the transaction pooler on `6543`) and `sslmode=verify-full`. Production rejects direct connections and other pooler modes because this application relies on session-level database behavior. The backend role must access the isolated `airtime` schema. Keep migration credentials server-side.
3. In Supabase Dashboard → Database Settings → SSL Configuration, download the project CA certificate. Base64-encode its PEM contents and set the result as the server-only `DATABASE_CA_CERT_BASE64` in Vercel and local secrets. On Linux use `base64 -w0 prod-ca-2021.crt`; on macOS use `base64 < prod-ca-2021.crt | tr -d '\n'`. Do not set a local certificate path in Vercel. AIRTIME decodes this value at runtime and passes it to node-postgres with `rejectUnauthorized: true`; it removes SSL query parameters from the sanitized driver URL so they cannot replace the explicit TLS options. Never log or commit the database URL, password, or encoded certificate.
4. Copy `.env.example` to `.env.local` and run `npm run db:migrate`. The migration runner applies ordered SQL in transactions, records `public.airtime_migrations` and uses an advisory lock. Existing installations apply only unapplied migrations; 003 adds Vibe automation and 004 adds paid-only durable provisioning and immutable provider identities; 005 makes embedded-only account IDs optional and binds each campaign to the single private AIRTIME advertiser. 006 adds immutable, creator/wallet-scoped private upload tickets and restrictive creator-object Storage policies. Apply 006 before deploying the direct-upload endpoints. Migration 007 derives and persists each ticket’s original extension from its immutable original filename; the approved MIME is already stored separately. Neither is proof of media. The original treasury schema is preserved. New installations apply 001 → 002 → 003 → 004 → 005 → 006 → 007 → 008. Back up real data first.
5. Migration 002 adds 19 tables: users, wallets, authentication challenges/sessions, coins/authority evidence, creator campaigns, creatives, targeting, invoices/payments, status history, metrics, reviews, refunds, creator messages, signed claim requests, operations audit and private proof. All have RLS; public grants are revoked. Unique signatures/invoices, exact-amount guards, immutable quotes and append-only payment/audit records enforce important invariants. All creator access goes through the scoped authenticated backend, not anonymous Supabase table queries.
6. Configure `SUPABASE_URL` / `SUPABASE_ANON_KEY` for the existing admin Auth implementation. Disable public email signup, create/confirm the `ADMIN_EMAIL` user, then provision the actual Auth UUID:

```sql
INSERT INTO airtime.admin_users(id,email)
VALUES ('ACTUAL_AUTH_USER_UUID','actual-allowlisted-email@example.com')
ON CONFLICT(id) DO NOTHING;
```

7. Enable TOTP and verify administrator AAL2 before using operations. Creator accounts are wallet-signature sessions and do not use Supabase password signup.
8. Create a PRIVATE `airtime-proof` storage bucket (or the server-only `SUPABASE_STORAGE_BUCKET`). Do not grant anonymous/public reads or writes. Configure the service role ONLY on the backend. Migration 006 forces the default bucket private and restricts browser Auth access to all `creators/` objects; signed uploads use Storage's server-side authority. The ticket endpoint also checks that the configured bucket is private on every operation. Configure the bucket file limit at least as high as `MAX_CREATIVE_BYTES` (default 25,000,000 bytes; supported 1–250 MB) and allow MP4, PNG/JPEG and existing PDF proof MIME types. Supabase plan/project limits may impose a lower maximum.
9. `POST /api/creator/upload` accepts an authenticated, bounded JSON declaration and returns a random creator-scoped upload ticket and signed URLs. The browser sends raw files directly to Supabase using PUT and visible progress. Only the configured Supabase origin is permitted by AIRTIME's browser CSP. No file body passes through the creator Vercel endpoints; neither the service key nor arbitrary storage paths are accepted from the browser.
10. Tickets can be finalized for 15 minutes. Supabase signed upload tokens have a fixed two-hour lifetime; they permit creation only at that ticket's quarantine path, with overwrite disabled. `POST /api/creator/upload/finalize` accepts only a ticket UUID, atomically claims it for the authenticated creator and wallet, verifies Storage size and the streamed size, and runs unchanged technical video checks. Storage video MIME may be `video/mp4` or `application/octet-stream`; actual MP4 box structure/signatures and FFprobe determine validity, never the filename or MIME alone. Leading padding boxes are supported, while missing/truncated boxes and non-video impostors fail closed. Video bytes stream to a generated temporary file under a hard byte limit and deadline, never a full-memory Blob. Validated files are copied to separate final paths that upload tokens cannot modify; only then is a technically valid creator creative inserted. Campaign attachment continues through the existing campaign save flow. Thumbnails use the same direct transport and server MIME/magic checks.
11. FFprobe uses the required production dependency `@ffprobe-installer/linux-x64` on Vercel, traced into the finalize function with its metadata and installer. `FFPROBE_PATH` remains an optional server-only local/custom override. Missing/unstartable executables return a safe 503; invalid videos are rejected and removed. `npm run build` reconstructs the finalize deployment using only traced files and tests the executable.
12. Keep the authenticated five-minute `/api/worker` scheduler active (see [HELIUS.md](HELIUS.md)). Both HTTP and CLI workers clean at most ten due tickets per run with deletion leases and retries. Expired/failed uploads and stale validation attempts are removed; validated final objects are preserved. Cleanup tombstones remain until 130 minutes after issuance, allowing another deletion after signed-token expiry to catch late uploads. Cancellation and validation failures immediately attempt deletion and retain durable cleanup work if Storage is unavailable. Do not delete ticket records before their cleanup finishes. Apply separate retention policies for validated media, old challenges/sessions and financial/audit records; never remove invoice/audit evidence as upload cleanup.

`npm run test` executes all eight migrations in ephemeral PGlite PostgreSQL, verifies all 51 tables’ RLS, retains a legacy record, and exercises direct-upload lifecycle, tenant isolation and financial SQL. Browser tests verify file bytes go only to signed Storage with the server-approved MIME header and AIRTIME receives JSON. A failed finalize consumes the ticket and performs cleanup itself; the browser shows the actual safe validation reason and requests a new ticket on the next upload, without sending a misleading DELETE against the consumed ticket. This does not claim that your remote Supabase project has been migrated or smoke-tested.

Migration 008 adds the disabled-by-default [admin-only TEST payment rail](PAYMENT_SMOKE_TEST.md), mandatory TEST audit labels and shared append-only reference/signature registries. Apply it before the production redeploy. The production build makes a read-only readiness check and holds deployment if payment schema guards or RLS are missing.
